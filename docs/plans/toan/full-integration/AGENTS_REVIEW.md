# Agent orchestration — Astra MAX review and implementation handoff

Reviewed 31 October 2026 at `33fbdd5`. Scope: execution of the five native roles, LangGraph negotiation, connection to Data operations/cards/seller decisions/night, and the orchestration side of durable recovery. Database, tools, Knowledge, self-improve, media, API/UI and hosting have separate reviews. This file is the only review output changed.

**Result: native core exists; the product integration is missing.** Keep Data as the only owner of business state. Add a local worker that consumes Data operations and invokes the existing graph/runner through scoped execution adapters. Do not run `app.runtime.day` alongside Data or create a second `Session.new` run. `HttpHarness` is an HTTP fixture, not the worker implementation or evidence of native agents.

## 1. Reuse these working pieces

- `app/agents/runner.py`: real `AIMessage.tool_calls` → validated bound tools → `ToolMessage(tool_call_id)` → typed `finish_<role>`. Three model requests per invocation, at most four calls per response, forced terminal on request three, output prerequisites and deterministic fallback.
- `app/agents/tools.py`: per-role allowlists, strict arguments, backend-bound run/shop/day, public/private DTO separation. Preserve these; an adapter must not return raw Data context or give models new mutation tools.
- `app/negotiation/graph.py`: genuine LangGraph Platform/Shop/Referee routing, exact counteroffer acceptance, final code checks and three platform rounds.
- `app/agents/content.py` and `app/memory/night.py`: native Content and Learning calls already exist. The media and SI lanes should adapt their context/publication boundaries, not replace them with prompt-only or fixture implementations.
- Data commands already own proposal checks, seller decisions, content approval, atomic publication/activation, campaigns, settlement, event sequence and night advancement. Use those commands and their idempotency receipts.

## 3. Concrete adapter shape

Use a new `app/runtime/data_worker.py` for the local orchestration loop and a small `app/infrastructure/data_agents.py` for scoped Data access/projection. Reuse the same `DataService` and SQLite file as the seller API. This can run in the backend process; external execution profile means Data delegates agent work, not that HTTP and another process are mandatory.

An execution context is disposable and contains no writable authoritative business state:

```text
AgentScope (frozen)
  run_id, day, shop_id, product_id, operation_id, negotiation_id, attempt
  brief_id/version, rules_version, inventory_version, cost_version, fee_policy_version
  knowledge_revision, pinned skill/version/snapshot identity (SI lane)

AgentExecutionContext
  scope + immutable public/private/brief/fee snapshots
  llm transport with durable per-run call ledger
  scoped Knowledge gateway
  scoped read/compute tool factory
  event sink and graph continuation/terminal receipt store

DataAgentBridge
  load_execution_scope(...), create_negotiation(...)
  record_turn(...), record_referee(...), finalize_negotiation(...), present(...)
  forecast_candidate(...), append_safe_agent_event(...)
```

Small compatibility views for `.states[shop_id]`, `.world.fees`, `.settings`, `.memory` and `.log` can avoid a large rewrite of existing feature callers. They are immutable snapshots/read adapters, not a `Session.new` object or a store of active state. Only orchestration metadata such as current source may be mutable. Native callers should accept injected tools/sinks where needed; the model still receives only each `BoundTool` DTO. Do not put seller personas in any execution context visible to roles.

Every bridge command uses Data's `command` transaction or an equivalently scoped internal service command with stable idempotency keys and body hashes. Local adapters must call `scope` with the appropriate server-selected role. Only the workflow bridge may write mutations; `BoundTool.execute` remains read/compute. Avoid SQL in `agents/runner.py`, domain models or feature prompts. Never hold a SQLite write transaction during a model/provider call.

Required mappings:

| Native value | Data value / invariant |
| --- | --- |
| `platform`, `shop`, `content`, `learning` | Server-bound roles `platform_agent`, `shop_agent`, `content_worker`, `learning_worker`; Referee emission uses the orchestrator service scope. Tokens/principals never enter prompts. |
| `PublicTurn.turn_id` | Stable native ID plus persisted proposal ID and public Data event seq; round is the actual platform-round count. |
| Shop `counter` | Proposal `stance=propose`, with distinct native action in transcript. Do not infer counters solely from an arbitrary history item. |
| `RefereeDecision.evidence_refs` | Lookup only in this attempt's persisted turn mapping; persist actual integer Data seq refs. |
| `NegotiationResult` | Data terminal status/rounds/exact final proposal/brief version; failed has no invented final package. Forecast displayed in card comes from Data's validated snapshot. |
| `Forecast` | Allowlist `low/point/high/factor_used/stock_warning` from Data candidate forecast; exclude raw private context. |
| Core event | Existing Data sequence, exact source identities and explicit `live/replay/offline/fixture`; private numerical values never serialized into shared telemetry. |

`finalize_negotiation` is the necessary small shared contract extension. Suggested body: expected negotiation version, terminal status, last/final proposal ID (nullable), bounded round count, safe reason, final referee receipt ID and graph receipt ID. Validate the operation/attempt owner, parent chain, round count, matching acceptance, exact package and current input versions. Successful status requires accepted final proposal plus completed Referee continuation; failed status is legal without a proposal. The same request returns its receipt; different body under the same key conflicts. Add `negotiation_finished` in that transaction and require it before card presentation. Preserve reference/harness behavior with an explicit profile-specific path; do not let it bypass external-native finalization.

## 4. Exact product call sequence

1. **Start day.** Seller confirms the brief; Data persists its identity. Seller `/api/day/start` creates the existing external `start_day` operation and returns promptly. Worker reads queued operation, claims its current version and keeps the returned owner/version. Create the run with `execution_profile=external`, `content_mode=worker`, `learning_mode=external`; run mode must explicitly drive live/offline/replay transport.
2. **Choose opportunities.** Read Data eligibility for A–E and current campaign state. Data already owns settlement/stop/expiry effects; do not run core monitor mutations a second time. Emit one real opportunity projection. Handle pending preference questions for active shops as Data question cards; do not renegotiate an active campaign. Distinguish renewal from an arbitrary `day>1` proposal using actual prior campaign expiry.
3. **Negotiate.** For each eligible shop, Data creates one negotiation under the operation. Pin brief, business versions, memory/skill context. Call real `run_negotiation` with the Data ID. Each role invokes `run_agent`; model-requested tools return real scoped Data/Knowledge results. Persist each actual turn and its mapping before the following Referee call; persist Referee verdicts. Checkpoint graph node/turn state and role receipt so a worker restart does not replay model calls. Keep all network calls outside write transactions.
4. **Finish and present.** Terminal graph result goes through Data finalization and current validators, then `present` creates the card. On safe failure, close the attempt and publish a truthful safe reason, without an offer card. Only finish the operation when every selected attempt is terminal and each successful final proposal was presented. No `reference_offer` or fabricated accept path is allowed in this worker.
5. **Other simulated shops.** Process A/B/C/E cards through the existing simulated-seller role/approval semantics, with the actual decisions recorded. Their content jobs go through the same worker/provider gates. Never use the harness's `first_safe`/fixture-memory policy as the native negotiation. D remains interactive. If no eligible offer exists, success can mean no card; it must still be safe to settle.
6. **Seller actions.** Existing Data facade owns Accept/Reject/Negotiate. Accept without refresh calls Data apply; refresh creates a persisted approved content job and waits. Negotiate resolves the old card and queues `renegotiate:<card_id>`; worker repeats steps 3–4 with a new Data attempt, the stored owner note and actual source card. Use Data's two additional attempt limit, separate from three platform rounds. Reject applies Data cooldown. Preference confirmation changes authoritative Rules only through its Data seller decision, then updates the derived preference record from that receipt.
7. **Content.** Media lane claims the actual content job and hydrates Content tool context using its current Data approval/brief/draft identity. It executes `generate_content` through the same durable native LLM transport, then the provider pipeline. Retry uses the persisted attempt and feedback; stale callbacks cannot change a later attempt. Seller Apply stays in Data's publication/activation transaction. See `MEDIA_REVIEW.md`; do not call core content application.
8. **Night.** Seller `/api/night` calls Data close: five settlements, immutable cutoff, pending learning handoff. Learning worker claims/heartbeats that handoff, obtains the SI/Knowledge public evidence projection at the Data cutoff, runs real Learning, commits Knowledge/publication durably and submits the exact receipt/summary. Data completes/advances once. Never call core `close_day` to simulate or advance again. Memory OFF skips learned writes/reads and Learning calls but still enforces authoritative Rules and all seller gates.
9. **Next invocation.** Read committed Knowledge effective for the new day, pin the attempt's policy, and demonstrate that confirmed style/history/skill appear in the actual tool result consumed by Content/Platform. A night summary alone is not evidence of learning. Seven-day completion is Data `complete` with `next_day=null`.

## 5. Budget, leases and crash recovery

- Share one durable LLM cap across **all five roles in the same Data run**. Reserve a unique call slot before invoking the transport, and never reset the cap on worker reconstruction. Key by `(run, negotiation-or-content-job-or-night, role, role-invocation, model-step)` and hash the frozen input/model/tool schema. Referee `run_name` currently uses brief ID and turn count (`referee.py`); add negotiation identity so separate attempts cannot collide.
- One negotiation can consume up to 36 model requests: three Platform invocations, three Shop invocations and six Referee invocations, each bounded at three. A 64-call demo cap can be exhausted before D if five shops run in lexical order. Prioritize the interactive D flow and explicitly account for Content/Learning; continue remaining work with labeled offline fallback when the shared cap is exhausted. Do not promise all shops/roles were live merely because the run mode is live.
- Retain SDK `max_retries=0`. Store every returned AI message/tool-call response before continuing; recovery can reconstruct the conversation and reuse deterministic read results/snapshots. Store the typed terminal role output and graph transition before writing a proposal. Replaying a proposal/card command uses the same stable request key, not a new attempt.
- Crash before reservation: safe to start. Reservation with no durable provider result: mark outcome unknown, consume the budget slot and **do not send that paid request again**. Choose explicit deterministic offline completion or a visible failed operation. Completed provider result with uncommitted business effect: reuse the result and command receipt. Completed operation/card: return existing state.
- Operation lease is 120 seconds; `operation_result(status=running)` renews it and increments version (`integration.py:124–125`). Run heartbeat separately from blocking graph calls and retain each returned version. Learning lease is 60 seconds with the same version discipline. Ensure cancellation/recovery cannot apply a late graph result after lease loss, day close or another claim.
- Close-day currently lacks an explicit queued/running agent-operation guard (`service.py:561–564`). Add it, or a caller can settle while a native graph is in flight and strand its writes. Likewise a failed operation must not make a still-running negotiation disappear from the night gate. Gate night on terminal attempts, resolved seller/content state and no unresolved paid work that can still mutate that day.
- Persist owner identity across restarts, or deliberately reclaim under a new owner through the versioned command. Recreating random principals on every poll changes command scope and defeats receipt reuse. Use the DB lane's shared call/operation ledger; no parallel JSON ledger or second EventLog sequence.
- Replay must not fall through to live when a key is present. Current `LLMClient` has no native response replay cache and simply falls back outside live mode. Implement durable recorded responses if replay is claimed; otherwise label it offline fallback honestly.

Required focused integration matrix:

1. **Real protocol:** fake model requests each role's mandatory tool, receives matching `ToolMessage`, consumes its result, then emits typed terminal output; public telemetry links that native invocation to Data proposal/card/job/night IDs. No pre-scripted fixture transcript substitution.
2. **D negotiation:** unsafe initial voucher/ads → real Shop code check/counter → exact Platform accept → Referee → Data final checks → one seller card. At most three platform turns. A changed package labeled accept fails. Third-round counter/failure terminates without a phantom card.
3. **Referee routing:** stop, ask-human, refocus and invalid same-role target; no unresolved Data negotiation or prematurely agreed/presented offer remains. Test provider/tool failure before the first turn and after an accepted turn.
4. **Privacy/scope:** capture model input and shared events. Platform/Referee/Content/Learning receive no private financial fields, persona or other-shop private memory; malicious tool args cannot switch run/shop/role. Include private numbers in owner notes/Shop/fallback text and assert sanitization at the outbound boundary.
5. **Seller/next day:** Accept → approved native Content → media fixture → explicit Apply → exactly one Data campaign. Negotiate carries the exact owner note/source card with bounded attempts; Reject cooldown; no pre-approval apply. Night uses exactly five Data settlements, one cutoff and one Learning publication; day 2 tools use committed learning/confirmed style. OFF still enforces Rules.
6. **Recovery/budget:** restart after reservation, after AI response, after terminal role output, after proposal, after card and after Knowledge commit. Verify one durable side effect, unchanged reservation count, no duplicate paid request, exact body conflict, rejected stale version and failed heartbeats. Concurrent claim has one winner; a lost-lease callback cannot publish.
7. **Model modes:** offline and replay-miss send zero network calls even with a configured key; cap exhaustion produces explicit offline source and leaves business flow recoverable. All five roles share the same per-run ledger; resetting the app does not replenish it.

## 7. Integration boundaries

Follow `SELF_IMPROVE_REVIEW.md` for frozen evidence, policy pinning and durable publication, and `MEDIA_REVIEW.md` for Content/provider/publication semantics. Business events used for learning must originate in the Data transaction with exact card/negotiation/package identities. Raw `learning-input` currently includes private views; the orchestration worker must consume the approved public evidence adapter, not forward that response to Learning.

Do not spend this lane's implementation time replacing FastAPI, LangGraph, the frontend, Data storage or the native runner. Do not expose a general LLM mutation API. The required new mechanisms are the scoped bridge, explicit graph finalization and durable execution receipts; they address concrete existing seams.

Not checked here: paid provider execution, media byte/playback behavior, browser UI, deployment and full seven-day empirical proof. No secrets were read or printed and no visible UI was opened. Main remaining risk: passing the existing native and Data suites independently still leaves all integration gates above unproven.
